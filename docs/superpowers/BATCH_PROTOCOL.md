# BATCH Protocol

## 1. 目的

BATCH 用于把大任务拆成 5-30 个可独立验证的子任务，并在人工审查通过后允许 3 个或 6 个子 Agent 并行推进。

BATCH 不是默认加速开关。共享接口、启动脚本、CMake、主题 token、`MainWindow`、`PanelManager` 等合流点默认串行处理。

## 2. 启动条件

必须同时满足：

- 已有 Specs 或 PRD。
- 子任务数量在 5-30 之间；少于 5 个默认串行，多于 30 个必须拆成多轮 BATCH。
- 子任务之间文件范围不重叠。
- 共享接口、命名、配置和验收命令已写清。
- 每个子任务都有三轴状态目标，且不允许子 Agent 自行提升状态。
- `CMakeLists.txt`、README、QSS、主窗口、PanelManager、公共接口和启动脚本已指定单一负责人。
- 失败后可以单独回滚或重做。
- 人工审查通过拆分方案。

## 3. 并行度

| 并行度 | 使用场景 |
|--------|----------|
| 1 | 默认值；共享入口、接口、构建、主题、架构边界 |
| 3 | 中等任务；文件互不重叠，验收可独立完成 |
| 6 | 大任务上限；5-30 子任务已拆清并通过人工审查 |

```markdown
|---|------|----------|----------|----------|----------|--------|
| 1 |      |          |          | E?/U?/D? |          | A |

## 人工审查

- 审查人：
- 审查时间：
- 结论：未审查 / 通过 / 退回修改
- 退回原因：

未填写“通过”前，子 Agent 只能做只读审计、复现和文档草案，不能并行写生产代码。

## 合流顺序

1. 先合流共享文档和接口。
2. 再合流独立实现。
3. 再由主 Agent 统一处理 CMake、README、QSS 等锁定文件。
4. 最后统一构建、测试和 `EmbedDebug.bat`。
5. 合流后只由主 Agent 提交，子 Agent 不直接 commit。

## 冲突处理

- 同文件冲突：停止并行，主 Agent 串行合并。
- 架构冲突：回到 Specs 修订。
- 构建失败：进入 LOOP Debug。
- 状态证据不足：不得提升三轴状态，回到对应子任务补验证。
```

## 5. 禁止事项

- 未经审查直接让多个子 Agent 写代码。
- 子 Agent 修改分配范围外的文件。
- 用并行扩大需求范围。
- 并行修改 `CMakeLists.txt`、启动脚本、全局主题 token 或核心入口。
- 把未通过构建的子任务合流为完成。
- 把“子任务完成”写成“整体完成”。
- 把 `E2骨架` 或 `E4单测通过` 写成 `U3用户主流程可用`。
- 在人工审查前启动 3 个或 6 个子 Agent 写代码。

## 6. BATCH 收口清单

- [ ] 子任务数量为 5-30。
- [ ] 人工审查结论为通过。
- [ ] 每个子任务只修改分配文件。
- [ ] 共享文件只由指定负责人修改。
- [ ] 三轴状态提升有证据。
- [ ] 构建、相关测试和受影响的启动链路已验证。
- [ ] 主 Agent 已检查 `git status --short` 和 staged diff。
- [ ] 主 Agent 已统一 commit；无法 commit 时写明阻塞原因。
