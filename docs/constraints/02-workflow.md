# 02 - 开发工作流与Agent角色

> 本文档描述迭代时的分流方式、协作原则和收口要求。  
> 具体的代码、UI、Git 细则仍以对应模块文档为准。

---

## 一、工作流分流

所有任务先分到下面 5 条线之一，再按各自流程执行。

### 1. PRD 线

适用场景:
- 新功能
- 行为变化
- 新组件
- 新接口

基本流程:
1. 明确目标、边界、验收条件
2. 补齐或更新 PRD
3. 做架构影响检查，确认是否涉及新类、跨层调用、公共组件复用
4. 再进入实现

要求:
- 没有 PRD 的功能需求，不进入编码
- 涉及新增类时，先做架构审查，再落代码
- 如果需求会影响既有行为，先列出兼容点和回归点

### 2. Bugfix 线

适用场景:
- 崩溃
- 编译失败
- 明确的逻辑错误
- 回归问题

基本流程:
1. 复现问题，记录触发条件和影响范围
2. 定级优先级，先处理阻断性问题
3. 定位根因，优先做最小修复
4. 补回归验证，确认没有引入新问题

要求:
- 先修复可复现的问题，再考虑优化
- 如果修复涉及架构边界，仍要补做架构影响检查
- P0/P1 问题未收敛前，新的高风险需求要暂缓

### 3. 技术债线

适用场景:
- 重构
- 拆分大文件
- 清理重复逻辑
- 提升可维护性
- 性能/可读性优化

基本流程:
1. 说明要偿还的技术债是什么
2. 标记当前行为不变的范围
3. 先做小步重构，再做必要的验证
4. 确认外部接口和关键行为保持一致

要求:
- 技术债任务要写清“改什么”和“不改什么”
- 涉及公共组件时，优先复用已有实现，不重复造轮子
- 如果目标只是整理代码，不要把需求扩展成新功能

### 4. 文档线

适用场景:
- 约束文档
- PRD
- 设计说明
- 使用说明
- 记录类文档

基本流程:
1. 先确认文档用途和受众
2. 更新正文、索引和引用关系
3. 检查术语、链接、版本号和过时信息
4. 如文档会影响执行规则，补上对应说明

要求:
- 纯文档变更通常不需要 PRD
- 但如果文档改动会改变执行方式，仍需先说明影响

### 5. 构建线

适用场景:
- 编译
- 打包
- 部署
- 启动验证
- 环境修复

基本流程:
1. 先确认当前目标是“验证”还是“修复构建”
2. 只改构建相关问题，不顺手扩大改动范围
3. 保持结果可复现
4. 输出明确的命令和结论

要求:
- 构建失败优先修到能稳定通过
- 启动验证要记录启动命令、结果和异常信息

## 二、Agent 协作原则

Agent 的数量不固定，按任务复杂度和依赖关系决定。

### 可并行时机

满足以下条件时，可以并行拆分:
- 任务彼此独立
- 不改同一批核心文件
- 接口已经稳定
- 失败后便于单独回滚或重做

### 不适合并行时机

出现以下情况时，优先串行:
- 多个任务共享同一接口草案
- 同一文件需要连续改动
- 需要先拿到一个任务的输出，后一个任务才能开始
- 改动范围较小，并行收益不高

### 推荐做法

- 先把边界、接口、验收条件定清楚，再拆分任务
- 能并行的部分，优先让互不依赖的工作同时推进
- 共享约定变更时，先收口到单一负责人或单一任务
- `run_in_background` 只在长耗时、互不阻塞的任务里使用，不作为硬性要求

## 三、角色分工

### 需求与设计

- 产品/需求角色负责澄清目标、边界、验收条件
- 架构角色负责依赖方向、接口划分、复用检查

### 实现与验证

- 开发角色负责编码实现
- 评审角色负责检查结构、可维护性和约束符合性
- 验证角色负责编译、启动和回归确认

### 合流规则

- 先完成接口对齐，再进入实现分支
- 评审意见要落到具体文件和具体修改点
- 有冲突时，先解决依赖和边界问题，再继续并行

---

## 四、收口要求

每次迭代收口时，至少确认下面几件事:

1. 相关任务已经被正确分流
2. PRD/bugfix/技术债/文档/构建各自的输出已归档
3. 编译结果明确
4. 启动验证结果明确
5. 需要复用或回收的公共组件已经对齐

如果某条线暂时不能完成，要把阻塞点写清楚，而不是用固定人数或固定并发策略硬推。
