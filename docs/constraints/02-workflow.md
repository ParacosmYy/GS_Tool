# 02 - 开发工作流与Agent角色

> 本文档描述迭代时的分流方式、协作原则和收口要求。  
> 具体的代码、UI、Git 细则仍以对应模块文档为准。

---

## 一、工作流分流

所有任务先判断主线，再按各自流程执行。一个任务只能有一个主线，必要时可以附带次标签，但不能同时拥有多个主线。

### 0-A. Specs / GO / BATCH / LOOP

超过单点修复的迭代必须先进入 Specs，再执行：

1. **Specs 定义**：先写目标、非目标、约束、验收标准、失败条件和验证命令。模板见 `docs/superpowers/specs/SPECS_TEMPLATE.md`。
2. **GO 执行**：按 execute → check → fix 循环推进。默认最多 20 轮或 30 分钟，工具骨架见 `tools/agent-loop/`。
3. **BATCH 拆分**：大任务拆成 5-30 个子任务，方案经人工审查后才允许 3 个或 6 个子 Agent 并行。协议见 `docs/superpowers/BATCH_PROTOCOL.md`。
4. **LOOP 监控**：失败按 Doctor / Debug / Simplify 分层处理，协议见 `docs/superpowers/LOOP_PROTOCOL.md`。

Specs 是执行边界，GO 是执行引擎，BATCH 是受控并行入口，LOOP 是失败处理路由。四者不得绕过 PRD、架构、UI、目录和启动验证约束。

### 0. 主线判定规则

按下面顺序判断主线，前一条命中后就停止：

1. **构建线**：编译、打包、启动、环境、依赖修复
2. **Bugfix 线**：修复已有缺陷、回归、崩溃、明确逻辑错误
3. **PRD 线**：新功能、新行为、新组件、新接口
4. **技术债线**：重构、拆分、清理重复逻辑、维护性优化
5. **文档线**：约束、PRD、说明、记录类文档

### 0.1 冲突消解

- 如果任务同时命中多个类别，以“当前最主要交付物”为主线。
- 如果主要交付物是验证环境或恢复构建，即使同时暴露了代码问题，也优先归入构建线。
- 如果主要目标是修复用户可见的缺陷，即使过程中需要少量重构，也优先归入 Bugfix 线。
- 如果主要目标是新增能力或改变行为，即使会顺带整理代码，也优先归入 PRD 线。
- 如果只是整理结构而不改变行为，则优先归入技术债线。

### 0.2 典型示例

| 场景 | 主线 | 次标签 |
|------|------|--------|
| 修正约束文档里的旧链接和过时表述 | 文档线 | 无 |
| 修复 `cmake --build` 失败 | 构建线 | 可附带 bugfix |
| 修复某个按钮点击崩溃 | Bugfix 线 | 可附带技术债 |
| 新增一个连接类型对话框 | PRD 线 | 可附带技术债 |
| 拆分过大的 `.cpp`，不改变行为 | 技术债线 | 可附带构建 |
| 修复构建失败并补一条文档说明 | 构建线 | 文档线仅作附带说明 |
| 新增 Serial Station 协议 | PRD 线 | 架构影响检查 + 协议测试 |
| 拆分 Serial Station 串口收发与协议解析 | 技术债线 | 必须加载 serial_station 架构 |

### 1. PRD 线

适用场景:
- 新功能
- 行为变化
- 新组件
- 新接口

基本流程:
1. 明确目标、边界、验收条件
2. 补齐或更新 PRD
3. 做架构影响检查，确认是否涉及新类、跨层调用、公共组件复用
4. 再进入实现

要求:
- 没有 PRD 的功能需求，不进入编码
- 涉及新增类时，先做架构审查，再落代码
- 如果需求会影响既有行为，先列出兼容点和回归点

### 2. Bugfix 线

适用场景:
- 崩溃
- 明确的逻辑错误
- 回归问题

基本流程:
1. 复现问题，记录触发条件和影响范围
2. 定级优先级，先处理阻断性问题
3. 定位根因，优先做最小修复
4. 补回归验证，确认没有引入新问题

要求:
- 先修复可复现的问题，再考虑优化
- 如果修复涉及架构边界，仍要补做架构影响检查
- P0/P1 问题未收敛前，新的高风险需求要暂缓
- 明确的编译失败只要不是产品缺陷本身，优先归入构建线

### 3. 技术债线

适用场景:
- 重构
- 拆分大文件
- 清理重复逻辑
- 提升可维护性
- 性能/可读性优化

基本流程:
1. 说明要偿还的技术债是什么
2. 标记当前行为不变的范围
3. 先做小步重构，再做必要的验证
4. 确认外部接口和关键行为保持一致

要求:
- 技术债任务要写清“改什么”和“不改什么”
- 涉及公共组件时，优先复用已有实现，不重复造轮子
- 如果目标只是整理代码，不要把需求扩展成新功能
- Serial Station 重构必须说明本次触碰的层：`ui`、`controller`、`core`、`protocols`、`services`、`workers`
- 单次 Serial Station 技术债默认只改一个层；跨层改动必须写清调用链和验证点

### 4. 文档线

适用场景:
- 约束文档
- PRD
- 设计说明
- 使用说明
- README / 宣传入口
- 记录类文档

基本流程:
1. 先确认文档用途和受众
2. 更新正文、索引和引用关系
3. 检查术语、链接、版本号和过时信息
4. 如文档会影响执行规则，补上对应说明

要求:
- 纯文档变更通常不需要 PRD
- 但如果文档改动会改变执行方式，仍需先说明影响
- 修改 Serial Station 边界时，必须同步更新 `docs/serial_station_architecture.md` 和相关约束索引

### 4.1 README 企业级宣传标准

`README.md` 是项目对外第一入口，后续更新必须按企业级开源项目标准维护，不能只写安装命令或零散说明。

README 更新要求:
- 首屏必须清楚表达项目名称、定位、核心价值、适用场景和当前成熟度。
- 必须包含精美且可维护的结构：功能亮点、截图或界面预览、架构概览、快速开始、构建环境、使用流程、路线图、贡献方式和许可证。
- 宣传表达可以专业、有质感，但不得夸大未落地能力；新增宣传点必须能在代码、文档或测试中找到对应证据。
- 涉及 UI、Serial Station、协议能力、构建方式或启动方式变化时，应同步检查 README 是否需要更新。
- README 中的命令必须能在本仓库当前约束下执行，构建目录只能写 `build/`，不得出现平行构建目录。
- README 中的截图、徽章、架构图和演示素材应使用仓库内稳定路径或可信链接，不能引用本地绝对路径、临时文件或 build 产物。
- 面向宣传的内容要服务真实产品能力：优先展示上位机工作流、串口调试、协议扩展、UI 体验和工程质量，而不是堆砌空泛口号。

### 5. 构建线

适用场景:
- 编译
- 打包
- 部署
- 启动验证
- 环境修复

基本流程:
1. 先确认当前目标是“验证”还是“修复构建”
2. 只改构建相关问题，不顺手扩大改动范围
3. 保持结果可复现
4. 输出明确的命令和结论

要求:
- 构建失败优先修到能稳定通过
- 启动验证要记录启动命令、结果和异常信息
- `EmbedDebug.bat` 双击能启动是最低验收线。只要改动影响构建、启动入口、资源路径、依赖部署、CMake、运行目录或 bat 脚本本身，收口前必须验证 bat 启动路径。
- 如果当前环境无法验证 bat 双击启动，必须写清具体原因，例如缺少 Qt、缺少 build 产物、缺少图形环境或工具链不可用，并给出一条可执行修复命令清单（如先跑环境检查脚本、补齐 PATH、再执行 `cmake --build`）。
- 构建目录只能是 `build/`。构建线任务不得创建或引用 `build2/`、`build-debug/`、`build-release/`、`cmake-build-*` 等平行目录。

## 二、Agent 协作原则

Agent 的数量不固定，按任务复杂度和依赖关系决定。

### 0. 受控并行入口

允许使用多个子 Agent 并行推进，但必须先经过 BATCH 拆分方案审查。

默认并行度：
- `1 个 Agent`：共享接口、CMake、启动脚本、主题 token、`MainWindow`、`PanelManager`、架构边界、构建修复等合流点任务。
- `3 个 Agent`：中等规模任务，且子任务改动文件互不重叠、接口已经稳定、验收点可独立验证。
- `6 个 Agent`：大型任务上限，仅用于 5-30 个子任务已经拆清楚、人工审查通过、且每个子任务有独立产物和回归命令的场景。

禁止为了“看起来更快”强行并行。并行的目标是缩短等待时间，不是扩大改动范围。

### 0.1 BATCH 拆分规则

在启动 3 个或 6 个子 Agent 前，必须先输出 BATCH 拆分方案，至少包含：

1. 总目标和本轮不做什么。
2. 5-30 个子任务清单。
3. 每个子任务的负责范围、可改文件、禁止改文件。
4. 每个子任务的验收命令或人工检查点。
5. 共享接口、数据结构、命名、token、CMake 注册方式。
6. 合流顺序和冲突处理方式。

BATCH 方案必须经过人工审查。未审查通过前，只允许做文档、审计、复现和只读分析，不允许多个子 Agent 同时写代码。

### 0.2 子 Agent 边界

每个子 Agent 必须遵守同一套仓库约束文档，不允许绕过 `CLAUDE.md`、架构分层、UI 标准、目录结构和 Serial Station 专项边界。

子 Agent 只能在分配范围内修改文件：
- 不允许擅自修改公共入口、CMake、主题 token、全局配置、启动脚本。
- 不允许改其他子任务负责的文件。
- 不允许创建平行目录、第二构建目录或临时生产入口。
- 不允许把未通过构建或未注册到 CMake 的 `.h/.cpp` 当作完成。

### 0.3 合流与验证

并行任务完成后必须串行合流，由主 Agent 做最终审查：

1. 检查所有子任务是否满足各自验收条件。
2. 检查是否出现同文件冲突、跨层 include、重复组件、重复 token。
3. 统一运行构建、测试和 `EmbedDebug.bat` 启动验证。
4. 把失败项回退到 Debug 或 Simplify 流程，不允许带失败合流。

合流失败时，不继续扩大并行度；先收敛接口、删除重复实现、恢复构建，再决定是否重新拆分。

### 可并行时机

满足以下条件时，可以并行拆分:
- 任务彼此独立
- 不改同一批核心文件
- 接口已经稳定
- 失败后便于单独回滚或重做

### 不适合并行时机

出现以下情况时，优先串行:
- 多个任务共享同一接口草案
- 同一文件需要连续改动
- 需要先拿到一个任务的输出，后一个任务才能开始
- 改动范围较小，并行收益不高

### 推荐做法

- 先把边界、接口、验收条件定清楚，再拆分任务
- 能并行的部分，优先让互不依赖的工作同时推进
- 共享约定变更时，先收口到单一负责人或单一任务
- `run_in_background` 只在长耗时、互不阻塞的任务里使用，不作为硬性要求

## 三、角色分工

### 需求与设计

- 产品/需求角色负责澄清目标、边界、验收条件
- 架构角色负责依赖方向、接口划分、复用检查

### 实现与验证

- 开发角色负责编码实现
- 评审角色负责检查结构、可维护性和约束符合性
- 验证角色负责编译、启动和回归确认

### 合流规则

- 先完成接口对齐，再进入实现分支
- 评审意见要落到具体文件和具体修改点
- 有冲突时，先解决依赖和边界问题，再继续并行

## 四、收口要求

每次迭代收口时，至少确认下面几件事:

1. 相关任务已经被正确分流
2. PRD/bugfix/技术债/文档/构建各自的输出已归档
3. 编译结果明确
4. 启动验证结果明确；涉及启动路径时必须包含 `EmbedDebug.bat` 结果
5. 需要复用或回收的公共组件已经对齐
6. 如果涉及 Serial Station，确认 UI/core/protocols/services/workers 没有越界依赖
7. 如果新增协议，确认对应 QTest 已加入 `tests/serial_station/`

如果某条线暂时不能完成，要把阻塞点写清楚，而不是用固定人数或固定并发策略硬推。

### 4.1 阶段提交要求

- 超过单点修复的任务必须按阶段提交，不允许把约束、构建、UI、业务代码、清理类改动混成一个大 commit。
- 推荐阶段顺序：约束/PRD/Specs → 构建与工具 → 生产代码 → 测试 → 清理与审计报告。
- 每个阶段 commit 前都必须完成该阶段能运行的最小验证；涉及构建、启动、CMake、bat、资源路径时必须验证 `EmbedDebug.bat`。
- 如果同一阶段无法独立验证，commit message 必须写明依赖的后续阶段和不能单独验证的原因。
- 主 Agent 负责串行合流和提交；子 Agent 不直接提交。
