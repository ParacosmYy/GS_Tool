# 02 - 开发工作流与Agent角色

> 本文档是 EmbedDebug 约束体系的第2模块。每次迭代必须遵循。

---

## 一、迭代流程

```
┌──────────────────────────────────────────────────────────────┐
│  Step 1: PRD需求文档     [产品经理]                            │
│    ↓ 输出: docs/prd/PRD_xxx.md                               │
├──────────────────────────────────────────────────────────────┤
│  Step 2: 需求评审         [系统架构师 + 产品经理]              │
│    ↓ 输出: 架构影响分析、公共组件复用检查                      │
├──────────────────────────────────────────────────────────────┤
│  Step 3: 架构设计         [系统架构师]                         │
│    ↓ 输出: 类图、接口定义、设计模式选型                       │
├──────────────────────────────────────────────────────────────┤
│  Step 4: 编码实现         [核心开发 + UI开发 + 协议开发]       │
│    ↓ 可并行: 核心/协议无依赖可同时开发                        │
├──────────────────────────────────────────────────────────────┤
│  Step 5: 集成联调         [集成开发]                           │
├──────────────────────────────────────────────────────────────┤
│  Step 6: 编译验证         [QA工程师]                           │
│    ↓ 约束: 零编译错误才能commit                               │
├──────────────────────────────────────────────────────────────┤
│  Step 7: 代码审查         [代码审查员]                         │
│    ↓ 约束: 设计模式合规、无重复代码、分层正确                  │
├──────────────────────────────────────────────────────────────┤
│  Step 8: Git Commit + Push                                    │
│    ↓ 评分: 本次commit +1分                                    │
└──────────────────────────────────────────────────────────────┘
```

## 二、Agent角色分配（11人团队，研发占比63.6%）

> **铁律**: 研发占比必须始终保持在 **60%~80%**。

| # | 角色 | Agent类型 | 职责 | 类别 |
|---|------|-----------|------|------|
| 1 | **产品经理** | `requirements-analyst` | 编写PRD，澄清需求边界 | 管理 |
| 2 | **系统架构师** | `system-architect` | 类图、接口、设计模式选型 | 研发 |
| 3 | **核心开发** | `general-purpose` | 基础设施层开发 | 研发 |
| 4 | **UI开发** | `frontend-architect` | 表现层开发 | 研发 |
| 5 | **协议开发** | `general-purpose` | 业务层协议/解析器开发 | 研发 |
| 6 | **集成开发** | `general-purpose` | 跨层集成、端到端联调 | 研发 |
| 7 | **UI/UX体验师** | `frontend-architect` | 观感评审 | 设计 |
| 8 | **代码审查员** | `self-review` | 代码质量审查 | 质量 |
| 9 | **QA工程师** | `quality-engineer` | 编译验证、测试 | 质量 |
| 10 | **新特性设计者** | `requirements-analyst` | 特性提案（每3次迭代） | 研发 |
| 11 | **新特性评审员** | `system-architect` | 评审提案（每3次迭代） | 研发 |

**并行策略**:
- Step 4: 角色3+5可完全并行；角色4等接口稳定后启动；角色6最后串联
- 角色7+8+9在编码完成后并行审查

## 三、架构管理审查（每5次commit）

审查人: 系统架构师。审查范围:
1. 分层架构合规性
2. 公共组件复用检查
3. 设计模式合规性
4. 模块间耦合度评估
5. 头文件引用规范
6. 新增类是否登记到公共组件清单
7. 目录结构是否按规划组织

---

## 四、新特性准入机制（每3次迭代）

### 评估流程
1. 新特性设计者 → 提交 1~3 个提案 (docs/prd/FEATURE_xxx.md)
2. 新特性评审员 → 评估: 用户价值/架构影响/开发成本/复用潜力
3. 通过 → 加入迭代；驳回 → 归档；暂缓 → 下轮再议

### 评估规则
- 每次最多通过 **1个** 提案
- 暂缓最多2次，超过则驳回
- 实现必须在通过后 **3个迭代内** 完成

---

## 五、Bug修复冲刺（每3次迭代）

**流程**:
1. 全面扫描所有已知Bug
2. 按优先级分类: P0(不可用) > P1(受限) > P2(体验)
3. **P0/P1优先修复**，新特性在Bug清零前暂停
4. 记录到 `docs/prd/BUG_AUDIT_xxx.md`

**铁律**: P0 Bug存在时禁止开发新特性。

---

## 六、多Agent并行工作流（每次迭代必须执行）

每次迭代启动 8 个 Agent:

| 波次 | Agent | 职责 |
|------|-------|------|
| 第一波 | 产品经理 + 架构师 | PRD + 设计并行 |
| 第二波 | 核心开发 + UI开发 + 协议开发 | 三路并行编码 |
| 第三波 | UI/UX审查 + 代码审查 + QA | 三路并行审查 |
| 汇总 | 主线程 | 修复问题 → 编译验证 → commit |

**强制要求**:
- 所有Agent使用 `run_in_background: true` 并行执行
- 主线程等待所有Agent完成后汇总
- 最终验证 `EmbedDebug.bat` 能正常启动
