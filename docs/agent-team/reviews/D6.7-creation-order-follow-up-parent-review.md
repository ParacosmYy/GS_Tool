## Pre-fix finding

The first D6.7 implementation called `Popen()` before `ProcessContainment.attach()`.
The protocol request was withheld until attachment, but the child could execute
interpreter startup and allocate resources before Job Object assignment. Luna
developer review `Hooke the 2nd` returned `REVISE` with this finding and also
identified that future timeout cleanup needed an explicit residual-risk record.

## Implemented correction

- `WindowsJobObjectContainment.launch()` creates and configures the Job Object
  before `Popen()`.
- Windows `Popen()` receives `CREATE_SUSPENDED`; no initial user-mode thread
  execution occurs before the process is assigned to the Job Object.
- `_Win32JobApi.resume_process()` enumerates the process's initial thread with
  `THREADENTRY32`, opens it with `THREAD_SUSPEND_RESUME`, and calls
  `ResumeThread()` only after assignment succeeds.
- Failure to create/configure/assign/open/resume terminates the child,
  closes stdio and Job handles, and maps to `containment-error` before a
  protocol request is sent.
- `SubprocessPluginHost` prefers the optional `launch()` seam. Existing
  attach-only adapters still use the compatibility path; they are not treated
  as a future external-execution security boundary.
- The immutable result still reports the configured limits and hard-coded
  `execution_enabled=false`.

## Disposition

`PROCEED WITH LIMITS`: the parent implementation and prior real Windows
evidence close the concrete default-path startup window, and the Terra findings
have been addressed in the source contract. D6.7 remains `in-progress` because
the hardened code has not received a new runtime or packaged smoke under the
user's no-launch constraint. This slice does not claim a complete sandbox,
restricted token, filesystem/network/secret isolation, signature trust,
dynamic loading, external execution, or certification.

## Residual verification and release limits

- The evidence is from the current Windows x64 environment only; clean-machine,
  cross-machine, permission/disk-pressure, and hard-power repeatability remain
  open.
- The attach-only compatibility seam is intentionally retained and is not a
  create-before-resume guarantee; it now reports `attached-after-start`. It
  must not become an external execution path without a separate security
  review and a mandatory creation-time containment capability.
- Parent Job Object nesting/incompatible policy behavior is fail-closed but not
  cross-machine verified.
- Signing, installer, update, legal, support, and clean-machine release gates
  remain open.
- Fresh Windows process/Qt/package evidence is intentionally unrun after the
  latest source change because starting the software is prohibited by the
  current user instruction.
