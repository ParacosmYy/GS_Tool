## Parent audit

- `application.plugin_enablement` owns the policy decision and mutation
  semantics; `PluginEnablementStore` is the only persistence seam. Neither
  service knows Qt, filesystem paths, plugin callbacks, or manager internals.
- `JsonPluginEnablementStore` validates a versioned ID/boolean schema, rejects
  duplicate IDs, caps reads at `max_bytes + 1`, caps records, and atomically
  replaces same-directory files after flush/fsync. Temporary files are cleaned
  on success and failure.
- A missing ledger resolves a trusted registration to enabled by default. A
  corrupt, unreadable, or oversized ledger resolves it disabled with a visible
  policy error. `persist()` reloads first and refuses mutation when the ledger
  is unavailable, so the UI cannot silently overwrite corrupt state.
- `PluginManager` resolves policy at registration and persists a trusted
  lifecycle intent before applying its existing manager-owned activation or
  cleanup. The runtime protocol still rejects enabling an untrusted plugin;
  external catalog entries never enter this registry.

## Disposition

D6.5 remains `in-progress` because the independent child review is unavailable
in this runtime. The implementation is limited to local policy for explicitly
registered in-process plugins. It does not claim publisher trust, signatures,
external module loading, process isolation, sandboxing, installation, updates,
remote policy, or release readiness.

## Unresolved risks

- No independent child review evidence is available for this increment.
- The policy is local preference state, not a security boundary; a user who can
  replace a valid policy can change the next startup decision.
- Activation/deactivation remains synchronous and in-process; an untrusted
  external runtime must use a future process-host protocol instead.
- Clean-machine, cross-machine, filesystem-pressure, hard-power, signing,
  installer, update, and legal/support release gates remain open.
