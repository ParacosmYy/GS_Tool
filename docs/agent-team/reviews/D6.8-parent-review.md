## Parent audit

- `application.plugin_execution` is a pure policy module. It owns typed
  evidence, frozen decisions, deterministic failure ordering, strict runtime
  evidence-shape validation, and the global `external_execution_enabled`
  threshold. It does not import modules, launch processes, access Qt, or write
  approval/enablement stores.
- The gate checks catalog validity, trust, approval/staleness, signature,
  code identity, explicit enablement, permissions, host containment, and
  executor availability. A malformed evidence object returns
  `invalid-evidence`; malformed fields are rejected before any untrusted value
  is hashed, and missing prerequisites cannot be interpreted as success.
- `PluginCatalogService` applies approval decoration first, then projects the
  gate result into immutable `PluginCatalogEntry` metadata. Every catalog entry
  is `execution=denied` under the current composition and remains untrusted,
  unloaded, and non-executable.
- `PluginCatalogEntry` stores only bounded diagnostic strings/tuples. The Qt
  dialog renders execution state, primary reason, and failed requirements; it
  has no loader callback or process handle.
- The composition root explicitly creates `PluginExecutionGate()` with the
  default disabled policy and injects it into `PluginCatalogService`. The
  existing in-process built-in plugin lifecycle and D6.7 diagnostic host path
  are unchanged.

## Disposition

D6.8 is `accepted-with-limits`: the parent repaired the malformed-evidence
fail-closed defect, documented the complete deny-reason set, and received a
post-fix independent Luna `PASS`. Actual external execution prerequisites and
security/release gates remain open. This increment proves explainable denial,
not executable plugins or a security certification claim.

## Unresolved risks

- A future change that enables execution still requires a separate high-risk
  security review and all prerequisite evidence; this source-only PASS does
  not authorize execution.
- A future change that turns the global policy on must bind signatures,
  publisher/code identity, permission grants, containment, executor lifecycle,
  installation/update provenance, and adversarial security review; the current
  gate alone is not sufficient authorization infrastructure.
- The current `PluginExecutionGate(external_execution_enabled=True)` can model a
  fully evidenced future decision, but no production composition enables it and
  no executor consumes an allowed decision. This distinction must remain in the
  acceptance contract.
- Clean-machine, cross-machine, permission/disk-pressure, hard-power,
  signing, installer, update, legal, and support release gates remain open.
