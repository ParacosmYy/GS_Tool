# D6.6 Windows handle conversion parent review

- **Date:** 2026-08-09
- **Delivery:** D6.6 process-isolated plugin host
- **Slice:** Windows Job Object native-handle conversion repair
- **Owner:** Architect (parent)
- **Disposition:** PROCEED WITH LIMITS; D6-AC06 and S19 remain `in-progress`

## Trigger and finding

The current source audit exercised the type boundary used by the Windows
containment adapter. `wintypes.HANDLE` is a `ctypes.c_void_p`; converting it
with `int(handle)` raises `ValueError` in the supplied Python runtime. The
same defect existed in `_Win32JobApi.create_job()` and
`_Win32JobApi.open_process()`, so the default Windows Job Object launch path
could fail before a diagnostic host was assigned.

The minimal repair changes both conversions to `int(handle.value)`. It keeps
the existing non-zero-handle checks, Win32 API signatures, Job Object policy,
creation-before-resume ordering, and cleanup behavior unchanged.

## Parent call-chain audit

- `SubprocessPluginHost` selects the creation-time containment launcher when
  available and keeps shell disabled, bounded stdio, timeout/kill, typed
  protocol errors, and launcher/reported PID provenance.
- `WindowsJobObjectContainment.launch()` creates/configures the Job Object,
  starts the child suspended, assigns it before resuming its initial thread,
  and closes the native lease on completion or failure.
- The fixed handle values are passed as integers only after reading the native
  `c_void_p.value`; snapshot and thread handles retain their existing ctypes
  lifecycle.
- `TaskRunner` retains the host probe until queued completion delivery, and
  `MainWindow` keeps the close guard active while the probe is in flight.
- The protocol remains one-shot, JSONL, 64 KiB frame-bounded, probe-only, and
  `execution_enabled=false`; no dynamic loader or external execution path is
  added.

## Public-source applicability

This is Python/Win32 desktop infrastructure, not embedded C/C++, MCU, BSP/HAL,
RTOS, ISR/DMA, or firmware work. The embedded vendor-source workflow is not
applicable. The existing ADR-0019/ADR-0028 records the applicable public
Microsoft Job Object/process/thread API references for the supported Windows
x64 scope; this slice makes no new manufacturer or security-certification
claim.

## Simplification assessment

The repair is intentionally two-line and local: a native `c_void_p` handle is
converted through its documented value field at the two API boundaries. A new
handle helper or broader containment refactor would enlarge the high-risk diff
without improving the current invariant, so it was deferred.
