# D7.4.2 follow-up parent review — startup restore cancellation

- **Date:** 2026-08-09
- **Delivery:** D7.4.2 TaskRunner lifecycle guard
- **Owner:** Architect (parent)
- **Disposition:** PROCEED WITH LIMITS; the startup barrier cancellation path is
  fixed and the independent Luna source audit returned PASS, while runtime
  evidence remains open

## Finding

The existing workspace-cancel path invalidated `_workspace_operation_id`,
`_active_operation_id`, and `_busy`, but did not release
`_session_restore_workspace_pending` when the cancelled operation belonged to
startup session restoration. The queued TaskRunner callback then correctly
became stale and returned from `_complete_operation()` before reaching the
normal workspace completion helper. That left the startup barrier permanently
set and blocked the remaining session restore queue.

## Fix audit

- `MainWindow._cancel_workspace_operation()` snapshots whether the workspace
  operation owns the startup restore barrier before invalidating operation
  state.
- After the UI cancellation projection is complete, the path calls the
  existing `_finish_session_workspace_restore()` helper only for that startup
  case.
- The workspace generation is still incremented, so the retained worker and
  its queued completion cannot mutate the new session-restore state.
- Normal user-initiated workspace cancellation keeps its existing behavior and
  does not enter the session restore queue.

  guarantee. This follow-up does not redesign that policy.
