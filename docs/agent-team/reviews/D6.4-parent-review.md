## Parent audit

- `application.plugin_runtime` owns the immutable `PluginRuntimeStatus` DTO and
  `PluginRuntime` protocol. Presentation depends on that contract rather than
  `PluginManager`, manifests, contexts, command registries, or widgets.
- `PluginManager` remains the sole owner of plugin callbacks, lifecycle
  contexts, command/event cleanup, and failure isolation. Its new
  `runtime_statuses()` method maps internal state into the application DTO.
- `set_enabled(True)` refuses an untrusted registered plugin; an enabled
  trusted plugin may activate only after the existing manifest/API gate. A
  disable deactivates first and removes owned commands/subscriptions before
  projecting `enabled=False`.
- `MainWindow` exposes **Tools → Plugin Status** and only forwards explicit
  enable/disable intents on the owning UI thread. The status dialog renders
  immutable values and never receives a plugin object or context.
- The composition root passes the manager through the protocol. The external
  catalog service and approval ledger are not connected to runtime activation;
  catalog entries remain `untrusted` and `loadable=False`.

## Disposition

D6.4 remains `in-progress` because the independent child review is unavailable
in this runtime. The implementation is limited to explicit in-process
lifecycle control and does not claim persisted enablement, external module
loading, signature verification, process isolation, sandboxing, installation,
updates, or release readiness.

## Unresolved risks

- No independent child review evidence is available for this increment.
- In-process plugin activation/deactivation is synchronous on the UI thread;
  a future untrusted/plugin-distribution path must not reuse it as a security
  or responsiveness boundary.
- Enablement is session-local and is not yet an enterprise policy source.
- Clean-machine, cross-machine, permission/disk-pressure, hard-power, signing,
  installer, update, and legal/support release gates remain open.
